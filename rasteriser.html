Software Rasteriser

Introduction

This project is my exploration of the concepts of rasterisation that I had learnt about in my Introduction to Computer Graphics course unit. I decided to use C++ for this project to get more familiar with the language and to provide more challenge compared to a higher level language like Python.

Current Features:

  • Parse .o files into a list of vertices, faces and vertex normals
  • Transform them using composite matrix multiplications
  • Project vertices into screen space using a perspective projection
  • Rasterises projected triangles with barycentric rasterisation
  • Interpolate colour values at each vertex

Project Overview

Before any maths for rendering could begin, A way to draw pixels to the screen was required. A simple low level, but well documented solution, was desired, landing me on SDL. It uses a texture which contains the pixel data shown on the screen, this is updated with a texture buffer which can be written to.

Afterwards, Vector and Matrix classes were created, since they are very important in computer graphics. They contained important functions implemented the common vector and matrix operations such as vector addition and matrix multiplication. A coordinate struct was also created to hold coordinates since they are needed often and this results in less overhead than using a vector for this. Before rendering 3D triangles, first a 2D triangle was attempted. Since 3D triangles are projected to two dimensions, this code can be reused when rendering 3D triangles.

In order to rasterise a triangle, each pixel is checked to see if it lies within the triangle. This was done using the barycentric method. This takes two of the sides of the triangle, and joins them with the point at the pixel we are checking to make a triangle and find its signed area using vectors operations. This is then done with the other two triangles created with the point to get three signed areas. If all 3 of these signed areas are not negative then the point is in the triangle.

To render 3D triangles, a way was needed to project 3D triangles onto a 2D plane. The initial way used was an orthographic projection, where the x and y coordinates are taken from the vertices and used while discarding the z coordinate.

To show 3D rendering more effectively, a rendering a whole 3D model was more suitable. This used a class to store models in, which is instantiated by reading object (.o) files. This was used to read a cube object file. The colours of the faces were randomly chosen to provide a distinction between the different faces

Since orthographic projection doesn't provide any sense of depth, A perspective projection was used instead. This involved a process called perspective division where you divide a vertice's x and y coordinates by the z coordinate, which causes further away objects to appear smaller.

After this, a more complex model was used to test the capabilities of the renderer. Blender's Suzanne model (a common test model) was used for this.

While it did render, two main issues were apparent

  • The performance was poor
  • Some of the triangles at the back of the monkey were rendering in front of it
To solve the first issue, an optimisation was made using bounding volumes. Instead of checking every pixel against every triangle, only the pixels that lie within the smallest rectangle that encompasses the triangle are checked. This is done by checking pixels between the minimum and maximum x and y coordinates of the triangle

The second issue was solved using a depth buffer. Whenever a pixel is drawn, it's z value is checked to see if it is less than what is currently stored in the z buffer, which is a buffer the same size as the framestore that stores the z values of the pixels plotted. In order to get z values for the pixels, they were interpolated from the 3 vertices of the triangle using the Barycentric areas as weights for each vertice's z value.

This provides a much smoother animation, with the hidden surfaces correctly removed. However, there were still many gaps present in the render.

The issue of gaps was fixed by correcting an off by one error in the code that tests whether a point is in the triangle. In addition to fixing this, the colours of the faces were changed. Now each vertex has an associated colour based on the direction of its vertex normal. Then these colours are interpolated, using the Barycentric areas, to fill in the inside of the triangle - this is called Gouraud Shading.

Conclusion

This project was designed as a way for me to have a go at implementing graphics concepts learned about in my degree. In that regard it has succeeded, however there are many more techniques that could be implemented in the future

Future Improvements

  • The CPU is used for rendering rather than the GPU which limits performance greatly. This is because I was more interested in learning and applying the rendering techniques than making a super performant rasteriser. While I don't have any plans to utilise the GPU, in the future, I may work to include more parallelism within the system
  • The model reader can only read .o files that are made up of triangles. In the future I will set up a system to create triangle fans out of larger polygons
  • Currently the triangles are rendered as random colours, but I would like to instead set the colour and use lighting and shading techniques
  • Models are rendered with small gaps between polygons
